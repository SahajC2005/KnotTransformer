Phase 2 · Buffer Box

The engine under the knots

How KnotTransformer turns N points into a knot vector, how the differentiable B-spline solver turns that vector into a curvature number, and what goes wrong at both ends of that chain.

The fact everything else hangs off

In construct_A the collocation rows are evaluated at t = knots[3 … N+2], which for a clamped vector is exactly [0, u₁ … u_K, 1]. So the interior knots are simultaneously the knot vector and the parameter values assigned to the data points.

When the model emits u₂ = 0.7 it is saying “data point 2 sits at t = 0.7 along the curve.” That is what “pacing” means, and it is the only quantity in the system that is free.

For N data points a clamped cubic B-spline has N + 6 knots, N + 2 control points and K = N − 2 free interior knots. The control points are not free — they fall out of a square solve A(u)·P = D̃. Interpolation is therefore free for any valid knot vector; only the shape changes. No fit-versus-smoothness trade-off exists, which is what makes the training self-supervised: there is no label, only an objective.

E(u) = ∫₀¹ κ(t)² · ‖C′(t)‖ dt        # squared curvature, integrated over arc length

Everything below the diagrams is computed, not quoted

This page carries a JavaScript port of curvature_layer_nd.py — Cox–de Boor basis, the collocation matrix with its natural end rows, the linear solve, the derivative recursions and the quadrature. It runs on the sample points stored in the notebook and reproduces the notebook's own energies to five significant figures:

Interpolation residual at every data point is below 1e-7, so these really are curves through the points. Having an independent implementation is what let the quadrature problem in section 08 surface at all.

The engine is deliberately not object-oriented

curvature_layer_nd.py and bspline3d.py define zero classes. Every piece of B-spline maths is a free function over tensors: construct, construct_A, solve_nd, de_boor, first_derivative_nd, second_derivative_nd, local_curvature_nd, global_curvature_nd, arc_nd, chordal_nd, centripetal_nd, dup, plus the 2-D aliases solve, global_curvature, arc.

That split is the right one. The model carries state and gets subclassed three ways; the solver is a pure function from (points, knots) to a scalar, so it needs no identity — and that is exactly what lets autograd treat it as one differentiable block.

The one piece of state the engine does carry is a module-level device global at curvature_layer_nd.py:28, with .to(device) on every internal temporary. That single mutable global is the origin of two separate failure modes further down this page.

04 · Attention

What the two attention stacks do here

Q = H·W_Q    K = H·W_K    V = H·W_V       # in_proj_weight, one 192×64 matrix, split in three
scores  = Q·Kᵀ / √d_k                        # d_k = 64 / 4 heads = 16
weights = softmax(scores)                     # masked at padded positions
out     = weights·V → out_proj              # 64×64 back to d_model

Encoder self-attention, N×N. Each point attends to every other. This is the capability the baselines structurally lack: chordal spacing is local, one chord length at a time, so knot placement near point 2 cannot react to a tight bend at point 5.

Decoder cross-attention, 6×N. Six learned query vectors, one per knot slot, each cross-attending to the point memory and emitting one knot. Parallel, DETR-style, not autoregressive. The decoder also self-attends among the six queries, which is how slot 3 coordinates with slot 2 rather than duplicating it.

This is the length-generalisation mechanism

The encoder absorbs any N ≤ 10 through attention plus a padding mask. The decoder slot count is fixed at max_knots = 6 and you read the first K. Training on N ∈ {4, 5} exercises slots 0–2 only. At N = 8 (K = 6) slots 3, 4 and 5 fire for the first time in their existence.

Two seeds, not three

The top-level README reports 75.7% ± 4.0% over three seeds. Both multi-seed cells in this notebook print Skipping seed 20260526 — no checkpoint and then (2 seeds). Whatever produced the three-seed figure, these stored outputs are not it — so the spread above is a two-point range, not a standard deviation worth quoting.

05 · Output head

Ordering for free, and the degree of freedom it costs

raw        = self.knot_head(decoded).squeeze(-1)        # (B, 6)
increments = F.softplus(raw) + 1e-6                     # strictly positive
cum        = torch.cumsum(increments, dim=-1)           # strictly increasing
knot_vals[b, :K] = cum[b, :K] / (cum[b, K-1] + 1e-8)   # → (0, 1]

Positive increments then a cumulative sum give strictly increasing knots by construction. No sorting, no constrained optimisation, fully differentiable — genuinely elegant, and why the model never emits an out-of-order knot vector.

But look at the divisor

It divides by cum[b, K-1] — the last element of the slice it is normalising. So knot_vals[b, K-1] == 1.0 identically, for every input, by algebra. The last predicted knot carries zero information.

K knots in, K − 1 real degrees of freedom out. Architectural, not a training artifact.

1.0 is also a degenerate knot — it collides with the clamped end knots and makes A singular. Hence the band-aid at generalization_experiment.py:98: rescale_knots_to_interior maps [0,1] into [0.02, 0.98].

You can read the pin straight out of the stored output. Cell 43:

Model κ: 107.65, knots: [0.15122412 0.27244648 0.90013417 0.97999999]

That trailing 0.97999999 is 0.02 + 0.96 × 1.0. It is not a prediction. Every model output in this repository ends in 0.98. The fix is already written elsewhere in the same notebook — cell 45's refiner parameterises K knots from K + 1 unconstrained reals:

def gaps_to_knots(theta):          # theta: (K+1,) unconstrained
    w  = torch.softmax(theta, dim=0)    # K+1 positive weights summing to 1
    cs = torch.cumsum(w, dim=0)[:-1]    # K strictly increasing values in (0,1)
    return EPS_KNOT + (1 - 2*EPS_KNOT) * cs

Predicting K + 1 increments and slicing K recovers the lost degree of freedom and removes the need for the rescale entirely. Two lines in the head.

06 · Engine

The differentiable solver

u  → construct            # Cox–de Boor basis values at a parameter t
   → construct_A          # (N+2)×(N+2) collocation + natural end rows
   → solve_nd             # C = inv_ex(A) · D̃    ← the differentiable bottleneck
   → first_derivative_nd  # Qᵢ = 3(Cᵢ₊₁−Cᵢ)/Δu
   → second_derivative_nd # Rᵢ = 2(Qᵢ₊₁−Qᵢ)/Δu
   → de_boor              # evaluate r′, r″ at quadrature points
   → global_curvature_nd  # ∫ κ²·speed dt  → scalar per sample

Deriving the cryptic end row

A[:, 0, 0] +=  knots[:, 5]
A[:, 0, 1] += -knots[:, 4] - knots[:, 5]
A[:, 0, 2] +=  knots[:, 4]

With u₁ = knots[4], u₂ = knots[5]: Q₀ = 3(P₁−P₀)/u₁, Q₁ = 3(P₂−P₁)/u₂, and R₀ ∝ (Q₁ − Q₀). Setting C″(0) = R₀ = 0:

u₂·P₀ − (u₁+u₂)·P₁ + u₁·P₂ = 0

Exactly those coefficients. So: clamped knot vector, natural end conditions. Both descriptions in the repo are right; they describe different things. Reproducing this row is what made the port match to five figures.

The lever that makes knots matter

Q[:, i] = 3 / (knots[:, i+4] - knots[:, i+1] + 1e-12) * (C[:, i+1] - C[:, i])

That denominator is a knot difference. Push two knots together and Q blows up. This is how spacing controls velocity and therefore curvature — and 1e-12 is all that stands between the model and a division by zero.

The gradient that ties it together

solve_nd forms the explicit inverse with torch.linalg.inv_ex, which is differentiable, so autograd silently derives implicit differentiation through the solve:

∂P/∂uₖ = −A⁻¹ (∂A/∂uₖ) P

That formula appears nowhere in the source. PyTorch derives it. It is the one ingredient connecting “where the knots are” to “what shape the curve is” differentiably, and it is what lets a curvature number at the end of the pipeline update transformer weights at the start.

inv_ex was chosen over a solve deliberately: it returns an info code instead of raising on a singular matrix. A degenerate knot vector therefore yields inf/NaN control points quietly, caught downstream by torch.isfinite. Convenient — and, as the buffer box shows, a trap.

07 · What the knots do

The same six points, two parameterisations

The notebook's cell-42 sample, solved on this page. Both curves pass through all six points exactly — that part is free. Everything different between them is the knot vector. Watch the frame size: the two panels are not at the same scale by default.

waypoint control point control point outside the box curve data bounding box curvature comb

Comb teeth point along the signed normal and are normalised per panel to that panel's own 90th-percentile curvature, because the two curves differ in κ by more than an order of magnitude — the combs show where each curve bends, and are not comparable between panels. The chart below is the comparable view.

The model's “smoother” curve is ten times the size of the data

The model's curve is not smoother in any everyday sense — it is bigger. It leaves the neighbourhood of the data entirely, sweeps a wide arc, and comes back through the remaining points. Take E(u) = ∫ κ² ds and let the interpolant detour at radius R: κ ≈ 1/R so κ² ≈ 1/R², while the detour's arc length grows like R. The contribution goes like R · 1/R² = 1/R.

Bigger loops have lower bending energy. The objective actively rewards ballooning outward and there is no arc-length term anywhere to stop it. A tenfold energy drop is a formally correct answer to the stated problem and a geometrically useless curve. This is why the model scores 68% on synthetic clouds and 13% on real GPS turns: on a road, nobody wants the balloon.

08 · Quadrature

The energies are grid artifacts

This is the one finding on the page that came out of building the figures rather than out of reading the code, and it is the most consequential.

global_curvature_nd integrates κ²·speed on a uniform grid of num_pts samples — 100 in every evaluation path, 50 during this notebook's training. Run the same integral at increasing resolution and it does not settle until roughly 1,600 points:

num_ptsChordal κModel κRatioUsed by

The integrand is the problem. It peaks at 6.3 × 10⁵ at t = 0.570 on the chordal curve while its median is about 1 — three orders of magnitude of dynamic range concentrated in a spike narrower than the grid spacing. A 100-point grid has Δt = 0.0101 and simply steps over it. Which samples happen to land near the peak then determines the answer, so the number is an aliasing artifact rather than an approximation.

Three things this breaks

  1. Absolute κ is wrong by 2–12×. On this sample the evaluation setting reports 711.5 against a true 2855.4 for chordal, and 68.4 against 139.2 for the model.
  2. The ratio is wrong by about 2×. num_pts = 100 gives 0.0962; the converged value is 0.0487. The ratio is the project's headline metric.
  3. The training objective is a different function from the evaluation metric. At N_QUAD = 50 the same two curves read 4936.8 and 16.1 — a ratio of 0.0033, off by a factor of 15, and wrong in the opposite direction for each curve. Phase 2 was not minimising a noisy version of the eval metric; it was minimising a different quantity.

Two caveats on scope, both important. This is one sample, and it was selected by cell 42 precisely for being hard (chord κ > 500), so it is the worst case rather than the typical one. And medians over 500 samples are more robust than any single value — aliasing error that is roughly symmetric across a population partly cancels in a median. Whether it does here is an open question that one sweep would answer: recompute the stored evaluation sets at num_pts = 2000 and see whether the win rates and ratios move. Until that is run, every absolute κ and every ratio in the repository should be treated as resolution-dependent.

The fix is cheap

Adaptive quadrature, or simply a much denser uniform grid — the integrand is smooth between spikes, so 2,000 points converges and costs 20× a forward pass of the solver, which is nothing next to training. For the training loop, where cost does matter, integrate on a grid refined near the knots, since that is where 3/Δu puts the spikes. Separately, the endpoint weights in (h/3)·(4·S1 + 2·S2) give the two end samples weight 2 instead of 1; that error is about 1% and is the least of the problems here.

09 · Buffer box

A correct idea at a catastrophic weight

You cannot easily penalise “the curve went too far” — that needs sampling and is non-smooth. But a B-spline lies inside the convex hull of its control points, so containing the control points contains the curve. And the control points are right there as the solver's output, differentiable with respect to the knots. Tick Buffer box in the viewer above to see which escape.

losses.py — the whole penalty

lo     = pts_g.min(dim=1).values              # (G,2)
hi     = pts_g.max(dim=1).values              # (G,2)
center = (0.5*(lo+hi)).unsqueeze(1)
half   = (0.5*(hi-lo)*(1.0+0.25)).unsqueeze(1)
excess = torch.clamp((Cc-center).abs()-half, min=0.0)
return (excess ** 2).sum()

Squared, so the penalty is C¹ at the box boundary — a plain |excess| would have a gradient kink there and fight Adam. Summed over G samples × (N+2) control points × 2 axes with no normalisation: an N = 8 sample has 10 control points against an N = 6 sample's 8, so identical geometric badness costs 25% more. This fine-tune mixes N ∈ {6, 7, 8}, so the penalty is silently N-biased.

Its gradient uses the energy's own path

C is not a free parameter — it came from the solve. So ∂penalty/∂θ = ∂penalty/∂C · (−A⁻¹(∂A/∂u)P) · ∂u/∂θ. The model has no control points to move; it is being told “choose knots whose induced solve keeps the control points near the data.” Same mechanism as the objective, second term.

Measured on this page

Computed exactly as losses.py does, for the two knot vectors in the viewer:

The idea discriminates perfectly — the sane curve is essentially free, the inflated one is not. It is the magnitude that is unusable.

Why λ = 200 destroyed the run

The penalty is in squared box-overshoot units; the energy is a curvature integral. Nothing makes them commensurate, so λ had to be calibrated, and it was not. For the sample above, λ · Σexcess² at λ = 200 is roughly a thousand times that sample's own energy. Even λ = 1 would make the penalty five times the energy. On samples like this one, every λ in the range I suggested earlier is still a hard constraint.

The penalty is zero inside the box, so the only way it can stall the energy is by pressing the optimiser permanently against the constraint. At λ = 200 any knot configuration that pushes a control point even slightly out costs more than the entire energy gain available, so the model retreats to the interior and stays. The box stops being a regulariser and becomes a hard constraint — and because control points legitimately overshoot the data for interpolating splines, the feasible set it carves out excludes good curves, not only bad ones.

What to change

  1. Make the excess dimensionless. Divide by half before squaring, so the penalty measures relative overshoot rather than overshoot in data units. Today a control point five box-widths out contributes its distance squared in raw coordinates, which is why one runaway point can dominate an entire batch.
  2. Use a Huber hinge, not a square. Quadratic growth on violations this large gives unbounded gradients from a single bad sample. A smooth-L1 beyond one box-width keeps the signal and bounds the pull.
  3. Normalise by (N+2)·2 so the penalty is a mean — removes the N-bias and makes λ transferable across lengths.
  4. Then calibrate λ against measurement rather than guessing, and ramp it from zero over the first few epochs so the model is not pinned to the box before it has learned anything.
  5. Log it. train_one_epoch already computes and returns box_mean; the fine-tune cell throws it away with train_loss = out[0]. Printing energy_loss, box_loss and λ·box_loss side by side would have diagnosed this on epoch 1 instead of after 49 minutes.

10 · Local minima

Does one forward pass land on a minimum?

Cell 45 compares the raw prediction against an L-BFGS refinement of it and against the best of 15 L-BFGS'd random restarts, on 100 held-out N = 6 samples.

refined / model = 0.9620 across all 97 valid samples is a strong finding: a second-order optimiser handed the model's answer cannot improve it — for 81.4% of samples by under 5%, for the median sample by 0.0%. One forward pass lands on a local minimum, in about a millisecond. That is the amortised-optimisation claim, cleanly demonstrated.

The engineering that makes it credible is the reparameterisation: theta ∈ ℝ^{K+1} is unconstrained and every theta maps to a valid ordered knot vector, so L-BFGS's strong-Wolfe line search never collides with a projection step. The earlier Adam refiners sort, clamp and force a minimum gap after every step, which fights the optimiser and stalls it.

With one caveat that section 08 adds

The objective L-BFGS was descending is the num_pts = 100 quadrature. On a spiky integrand that grid is aliased, so part of what the refiner was climbing out of — and part of what it concluded was flat — belongs to the grid rather than to the energy. “The model sits at a local minimum of the computed objective” is established. “Of the true bending energy” needs the same run at converged resolution.

11 · Defects

Four things to fix before anything is published

1 · The quadrature does not resolve the integrand

Section 08 in full. num_pts = 100 misstates absolute κ by 2–12× and the ratio by about 2× on a hard sample; N_QUAD = 50 in training misstates the ratio by 15× and in the opposite direction for each curve. Sweep the stored evaluation sets at converged resolution before reporting any κ or any ratio.

2 · The heatmap's local-minimum marker is plotted at the wrong point

best_k_this = init.copy()
...
    if k_eval < best_kappa_this:
        best_kappa_this = k_eval
        best_k = knots.detach().numpy().copy()   # writes best_k
if best_kappa_this < best_overall_kappa:
    best_overall_kappa = best_kappa_this
    best_overall_k     = best_k_this             # reads best_k_this

best_k is a dead store; best_k_this is never updated after initialisation. The function returns an improved κ paired with the initial random knots. Everything downstream inherits it: k1_fixed and k4_fixed define the slice the heatmap is computed on, so curvature_landscape_v2.png is a slice through an arbitrary point with a mismarked optimum. One-line fix: best_k_this = knots.detach().numpy().copy().

3 · The device global makes results depend on cell execution order

Cell 42 sets cl.device = DEVICE (CUDA) then builds CPU tensors. construct allocates CUDA temporaries internally, they meet CPU inputs, a RuntimeError is raised, and except Exception: break swallows it on iteration zero. The stored output confirms it:

Local min knots   : [0.0342271 0.04479033 0.96740919 0.98]  # identical to the model's
  curvature       : inf

So cell 42's local-minimum result is an artifact, not a finding. Cell 45's trace does show real improvements, which means it ran in a session where cl.device was CPU — the validity of that experiment depends on which cells you ran first.

Root fix: derive the device from the inputs (dev = knots.device) throughout construct, de_boor, solve_nd and the derivative functions. That makes the solver device-agnostic and deletes both the cell-18 monkey-patch and this whole class of silent failure.

4 · The box penalty can poison a whole batch

batch_box_sum.append(buffer_box_penalty(C, pts_g))   # BEFORE the finite check
finite = torch.isfinite(eng)
eng_ok = eng[finite]                                  # energy drops bad samples

The energy term carefully drops non-finite samples; the box term does not — it is computed on the whole group's C before any filtering. When inv_ex hits a near-singular A, C holds inf/NaN, the energy is correctly dropped, and the box penalty still enters the loss. Then loss is NaN, backward() gives NaN gradients, clip_grad_norm_ does not remove them (it scales by a norm that is itself NaN), and optim.step() writes NaN into the weights.

It evidently did not fire in the stored run. But nan_skips is returned by train_one_epoch and discarded by the caller, so there is no evidence either way. Mask the box term by finite too, and guard with if not torch.isfinite(loss): continue.

Summary

Four sentences

  1. Knots are the only free variable, and they are simultaneously the knot vector and the data parameterisation — “pacing” is the right intuition.
  2. The entire chain is differentiable, the linear solve included, so the curve's own curvature is the training signal and no label exists anywhere in the system.
  3. The buffer box is the right idea at the wrong weight and in the wrong units: the energy genuinely rewards inflation, the convex-hull property gives a differentiable handle on it, but raw squared overshoot at λ = 200 is a hard constraint whose feasible set excludes the good solutions.
  4. Underneath all of it, the quadrature does not resolve the integrand it is integrating, so the absolute energies, the headline ratios and the training signal are all resolution-dependent — which is the first thing to fix, because every other number depends on it.

In order: sweep the evaluation sets at converged quadrature, recover the pinned degree of freedom in the output head, make the solver device-agnostic, re-specify the box penalty in relative units with a Huber hinge, and run the trip-split notebook.
