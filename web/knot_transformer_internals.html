The engine under the knots

An encoder–decoder transformer predicts the four numbers that set a B-spline's internal pacing. A differentiable solver turns those numbers into a curvature score, and that score is the only training signal. This page takes the whole chain apart — and recomputes it, so you can move the knots yourself.

The fact everything else hangs off

In construct_A the collocation rows are evaluated at t = knots[3 … N+2], which for a clamped vector is exactly [0, u₁ … u_K, 1]. The interior knots are simultaneously the knot vector and the parameter values assigned to the data points.

So when the model emits u₂ = 0.7 it is saying “data point 2 sits at t = 0.7 along the curve.” That is what pacing means, and it is the only quantity in the system that is free. For N points there are N+6 knots, N+2 control points and K = N−2 degrees of freedom. The control points are not free — they fall out of A(u)·P = D̃. Interpolation is free for any valid knot vector; only the shape changes.

Everything below is computed, not quoted
This page carries a JavaScript port of curvature_layer_nd.py — Cox–de Boor basis, the collocation matrix with its natural end rows, the linear solve, the derivative recursions, the quadrature. It runs on the sample points stored in the notebook.
Matching the notebook to five significant figures means the end-condition rows, the half-open-interval case at t = 1 and both derivative recursions are reproduced correctly. Having an independent implementation is what let the quadrature defect surface at all.

04 · Attention

What the two attention stacks do here

No trained weights ship with the repo, so there are no attention values to show. The structure is the interesting part anyway — it is what the baselines structurally cannot do.

The projection algebra
Q = H·W_Q   K = H·W_K   V = H·W_V   one 192×64 in_proj, split in 3
scores  = Q·Kᵗ / √d_k               d_k = 64/4 heads = 16
weights = softmax(scores)            masked at padded positions
out     = weights·V → out_proj      64×64 back to d_model
Four heads on 16-dimensional slices, so each head can specialise — one on arc position, another on local turning. interpretability.py exists to probe which.
Attention shapes
Encoder self-attention is N×N; decoder cross-attention stays 6×N for every N.

Encoder self-attention, N×N. Each point attends to every other. Chordal spacing is local — one chord length at a time — so knot placement near point 2 cannot react to a tight bend at point 5. Self-attention makes exactly that dependence representable.

Decoder cross-attention, 6×N. Six learned query vectors, one per knot slot, each cross-attending to the point memory and emitting one knot. Parallel, DETR-style, not autoregressive. The decoder also self-attends among the six queries, which is how slot 3 coordinates with slot 2 rather than duplicating it.

This is the length-generalisation mechanism

The encoder absorbs any N ≤ 10 through attention plus a padding mask. The decoder slot count is fixed at max_knots = 6 and you read the first K. Training on N ∈ {4, 5} exercises slots 0–2 only. At N = 8 (K = 6) slots 3, 4 and 5 fire for the first time in their existence — and the result is degenerate: 0, 500/500 valid, best ratio of the five lengths.

05 · Output head

Ordering for free, and the degree of freedom it costs

Positive increments then a cumulative sum give strictly increasing knots by construction — no sorting, no constrained optimisation, fully differentiable. Genuinely elegant. The normalisation is where it goes wrong.

Drive the head yourself
Four sliders stand in for the decoder's raw logits. Watch the pipeline run — and watch the last knot.
raw        = self.knot_head(decoded).squeeze(-1)
increments = F.softplus(raw) + 1e-6                     strictly positive
cum        = torch.cumsum(increments, dim=-1)           strictly increasing
knot_vals[b, :K] = cum[b, :K] / (cum[b, K-1] + 1e-8)   ← the divisor
Move any slider. The first three knots respond; u₄ reads 1.000000 for every possible input, because the divisor is the last element of the slice being normalised. That is algebra, not a trained behaviour.
K knots in, K−1 degrees of freedom out

The last predicted knot carries zero information. It is also a degenerate knot — 1.0 collides with the clamped end knots and makes A singular — which is why rescale_knots_to_interior exists at generalization_experiment.py:98, mapping [0,1] into [0.02, 0.98]. You can read the pin straight out of cell 43's stored output:

Model κ: 107.65, knots: [0.15122412 0.27244648 0.90013417 0.97999999]

Every model output in this repository ends in 0.98. It is 0.02 + 0.96 × 1.0, not a prediction.

The fix is already written, further down the same notebook
Cell 45's L-BFGS refiner parameterises K knots from K+1 unconstrained reals.
def gaps_to_knots(theta):          theta: (K+1,) unconstrained
    w  = torch.softmax(theta, dim=0)    K+1 positive weights summing to 1
    cs = torch.cumsum(w, dim=0)[:-1]    K strictly increasing values in (0,1)
    return EPS_KNOT + (1 - 2*EPS_KNOT) * cs
Predict K+1 increments and slice K. Recovers the lost degree of freedom, removes the need for the rescale entirely, and keeps ordering by construction. Two lines in the head.

06 · Solver

The differentiable bottleneck

Pure functions, float64 throughout, every step batched. This is what makes the project possible — and what the port had to reproduce exactly to match the notebook.

A(u) for N = 6 → 8 × 8
Row labels name what each row constrains.
The 4-wide band is the local support of a cubic basis. The single cells at t = 0 and t = 1 are clamping: C(0) = P₀, C(1) = P₇, the latter hardcoded because construct's intervals are half-open.
Deriving the cryptic end row
A[:, 0, 0] +=  knots[:, 5]
A[:, 0, 1] += -knots[:, 4] - knots[:, 5]
A[:, 0, 2] +=  knots[:, 4]

With u₁ = knots[4], u₂ = knots[5]: Q₀ = 3(P₁−P₀)/u₁, Q₁ = 3(P₂−P₁)/u₂, R₀ ∝ (Q₁ − Q₀). Setting C″(0) = R₀ = 0 gives u₂·P₀ − (u₁+u₂)·P₁ + u₁·P₂ = 0 — exactly those coefficients. So: clamped knot vector, natural end conditions. Both descriptions in the repo are right; they describe different things.

The lever that makes knots matter
Q[:, i] = 3 / (knots[:, i+4] - knots[:, i+1] + 1e-12)
          * (C[:, i+1] - C[:, i])

That denominator is a knot difference. Push two knots together and Q blows up. This is how spacing controls velocity and therefore curvature — and 1e-12 is all that stands between the model and a division by zero.

∂P/∂uₖ = −A⁻¹ (∂A/∂uₖ) P

That formula appears nowhere in the source. solve_nd forms the explicit inverse with torch.linalg.inv_ex, which is differentiable, so autograd derives implicit differentiation through the solve by itself. It is the one ingredient connecting “where the knots are” to “what shape the curve is” differentiably — and what lets a curvature number at the end of the pipeline update transformer weights at the start.

inv_ex fails quietly, by design

It returns an info code instead of raising on a singular matrix, so a degenerate knot vector yields inf/NaN control points silently, caught downstream by torch.isfinite. Convenient — and, as the buffer box shows in section 09, a trap.

The model's “smoother” curve is ten times the size of the data

The model's curve is not smoother in any everyday sense — it is bigger. It leaves the neighbourhood of the data entirely, sweeps a wide arc, and comes back through the remaining points. Take E(u) = ∫ κ² ds and let the interpolant detour at radius R: κ ≈ 1/R so κ² ≈ 1/R², while the detour's arc length grows like R. The contribution goes like R · 1/R² = 1/R.

Bigger loops have lower bending energy. The objective actively rewards ballooning outward and there is no arc-length term anywhere to stop it. A tenfold energy drop is a formally correct answer to the stated problem and a geometrically useless curve. This is why the model scores 68% on synthetic clouds and 13% on real GPS turns.

09 · Quadrature

The energies are grid artifacts

This is the one finding that came out of building the figures rather than reading the code, and it is the most consequential thing on the page.

See the grid step over the spike
The integrand κ²·speed on a log axis, with the actual sample points the repo uses drawn on top.
The chordal integrand peaks at 6.3 × 10⁵ at t = 0.570 while its median is about 1 — three orders of magnitude of dynamic range inside a spike narrower than the grid spacing. At num_pts = 100, Δt = 0.0101. Which samples happen to land near the peak determines the answer, so the number is an aliasing artifact rather than an approximation.
Convergence sweep
The repository's own quadrature formula, resolution swept. Dashed lines are the converged values.
What each resolution reports
Three things this breaks
  1. Absolute κ is wrong by 2–12×. On this sample the evaluation setting reports 711.5 against a true 2855.4 for chordal, and 68.4 against 139.2 for the model.
  2. The ratio is wrong by about 2×. num_pts = 100 gives 0.0962; converged is 0.0487. The ratio is the project's headline metric.
  3. The training objective is a different function from the evaluation metric. At N_QUAD = 50 the same two curves read 4936.8 and 16.1 — ratio 0.0033, off by a factor of 15, and wrong in the opposite direction for each curve. Phase 2 was not minimising a noisy version of the eval metric; it was minimising a different quantity.
Two caveats on scope

This is one sample, selected by cell 42 precisely for being hard (chord κ > 500), so it is the worst case rather than the typical one. And medians over 500 samples are more robust than any single value — aliasing error that is roughly symmetric across a population partly cancels in a median. Whether it does here is an open question that one sweep would answer: recompute the stored evaluation sets at num_pts = 2000 and see whether the win rates move. Until that is run, every absolute κ and every ratio in the repository should be treated as resolution-dependent.

The fix is cheap

The integrand is smooth between spikes, so 2,000 uniform points converges and costs 20× one solver pass — nothing next to training. For the training loop, where cost does matter, integrate on a grid refined near the knots, since that is where 3/Δu puts the spikes. Separately, the endpoint weights in (h/3)·(4·S1 + 2·S2) give the two end samples weight 2 instead of 1; that error is about 1% and is the least of the problems here.

10 · Buffer box

A correct idea at a catastrophic weight

You cannot easily penalise “the curve went too far” — that needs sampling and is non-smooth. But a B-spline lies inside the convex hull of its control points, so containing the control points contains the curve. And the control points are right there as the solver's output, differentiable with respect to the knots.

losses.py — the whole penalty
lo     = pts_g.min(dim=1).values
hi     = pts_g.max(dim=1).values
center = (0.5*(lo+hi)).unsqueeze(1)
half   = (0.5*(hi-lo)*(1.0+0.25)).unsqueeze(1)
excess = torch.clamp((Cc-center).abs()-half, min=0.0)
return (excess ** 2).sum()

Squared, so the penalty is C¹ at the boundary — a plain |excess| would have a gradient kink there and fight Adam. Summed over G samples × (N+2) control points × 2 axes with no normalisation: an N = 8 sample has 10 control points against an N = 6 sample's 8, so identical geometric badness costs 25% more. This fine-tune mixes N ∈ {6, 7, 8}, so the penalty is silently N-biased.

Measured on this page
Computed exactly as losses.py does, including your current knots.
The idea discriminates perfectly — the sane curve is essentially free, the inflated one is not. It is the magnitude that is unusable.
Its gradient rides the energy's own path

C is not a free parameter — it came from the solve. So ∂penalty/∂θ = ∂penalty/∂C · (−A⁻¹(∂A/∂u)P) · ∂u/∂θ. The model has no control points to move; it is being told “choose knots whose induced solve keeps the control points near the data.”

Why λ = 200 destroyed the run
The penalty is in squared box-overshoot units; the energy is a curvature integral. Nothing makes them commensurate, so λ had to be calibrated — and it was not.

What to change
  1. Make the excess dimensionless. Divide by half before squaring, so the penalty measures relative overshoot. Today a control point five box-widths out contributes its distance squared in raw coordinates, which is why one runaway point can dominate a batch.
  2. Use a Huber hinge, not a square. Quadratic growth on violations this large gives unbounded gradients from a single sample. Smooth-L1 beyond one box-width keeps the signal and bounds the pull.
  3. Normalise by (N+2)·2 so it is a mean — removes the N-bias, makes λ transferable across lengths.
  4. Then calibrate λ against measurement and ramp it from zero over the first epochs, so the model is not pinned to the box before it has learned anything.
  5. Log it. Print energy_loss, box_loss and λ·box_loss side by side — that would have diagnosed this on epoch 1 instead of after 49 minutes.

12 · Defects

Four things to fix before anything is published

Ordered by how much they invalidate. The first one touches every number in the repository.

Section 09 in full. num_pts = 100 misstates absolute κ by 2–12× and the ratio by about 2× on a hard sample; N_QUAD = 50 in training misstates the ratio by 15×, in opposite directions for the two curves. Sweep the stored evaluation sets at converged resolution before reporting any κ or any ratio.

best_k_this = init.copy()
...
    if k_eval < best_kappa_this:
        best_kappa_this = k_eval
        best_k = knots.detach().numpy().copy()   # writes best_k
if best_kappa_this < best_overall_kappa:
    best_overall_kappa = best_kappa_this
    best_overall_k     = best_k_this             # reads best_k_this

best_k is a dead store; best_k_this is never updated after initialisation. The function returns an improved κ paired with the initial random knots. Everything downstream inherits it: those knots set k1_fixed and k4_fixed, which define the slice the heatmap is computed on. So curvature_landscape_v2.png is a slice through an arbitrary point with a mismarked optimum. One-line fix: best_k_this = knots.detach().numpy().copy(). Section 08 above is the corrected version.

Cell 42 sets cl.device = DEVICE (CUDA) then builds CPU tensors. construct allocates CUDA temporaries internally, they meet CPU inputs, a RuntimeError is raised, and except Exception: break swallows it on iteration zero. The stored output confirms it:

Local min knots   : [0.0342271 0.04479033 0.96740919 0.98]  # identical to the model's
  curvature       : inf

So cell 42's local-minimum result is an artifact, not a finding. Cell 45's trace does show real improvements, which means it ran in a session where cl.device was CPU — the validity of that experiment depends on which cells you ran first.

Root fix: derive the device from the inputs (dev = knots.device) throughout construct, de_boor, solve_nd and the derivative functions. That makes the solver device-agnostic and deletes both the cell-18 monkey-patch and this whole class of silent failure.

batch_box_sum.append(buffer_box_penalty(C, pts_g))   # BEFORE the finite check
finite = torch.isfinite(eng)
eng_ok = eng[finite]                                  # energy drops bad samples

The energy term carefully drops non-finite samples; the box term does not — it is computed on the whole group's C before any filtering. When inv_ex hits a near-singular A, C holds inf/NaN, the energy is correctly dropped, and the box penalty still enters the loss. Then loss is NaN, backward() gives NaN gradients, clip_grad_norm_ does not remove them (it scales by a norm that is itself NaN), and optim.step() writes NaN into the weights.

It evidently did not fire in the stored run. But nan_skips is returned by train_one_epoch and discarded by the caller, so there is no evidence either way. Mask the box term by finite too, and guard with if not torch.isfinite(loss): continue.

Summary

Four sentences and an order of work

  1. Knots are the only free variable, and they are simultaneously the knot vector and the data parameterisation — pacing is the right intuition.
  2. The entire chain is differentiable, the linear solve included, so the curve's own curvature is the training signal and no label exists anywhere in the system.
  3. The buffer box is the right idea at the wrong weight and in the wrong units: the energy genuinely rewards inflation, the convex-hull property gives a differentiable handle on it, but raw squared overshoot at λ = 200 is a hard constraint whose feasible set excludes the good solutions.
  4. Underneath all of it the quadrature does not resolve the integrand it is integrating, so the absolute energies, the headline ratios and the training signal are all resolution-dependent.
In order
  1. Sweep the evaluation sets at converged quadrature. Everything else is measured through this.
  2. Recover the pinned degree of freedom in the output head — the code already exists in cell 45.
  3. Make the solver device-agnostic.
  4. Re-specify the box penalty in relative units with a Huber hinge, then calibrate λ.
  5. Run Phase2_RealTurns_TripSplit.ipynb; the 15-turn results cannot support a conclusion either way.
