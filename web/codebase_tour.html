Codebase tour · KnotTransformer

A transformer that chooses where a spline spends its time

Any ordered set of waypoints has infinitely many cubic B-splines through it. The only free choice is the knot vector, and one choice bends least. This repo trains a DETR-style encoder–decoder to pick those knots in a single forward pass, graded by the curve's own bending energy. This page walks through the files, the three model variants, the training loops, and exactly which parts of DETR survived the trip.

Architecture

Points in, ordered knots out

The forward pass in KnotTransformer.forward (knot_transformer.py:236) is three lanes. The encoder reads the waypoints. The decoder asks six fixed questions of what the encoder wrote. During Phase 2 a third lane turns the answers into a curve and measures it.

What each waypoint token contains

Built in compute_geometric_features, concatenated with raw (x, y), then lifted by Linear(6, 64).

Three details that are easy to miss

  • The decoder is never told K. num_knots is used only after the head, to choose which cumulative sum to divide by. All six queries always run. The network has to infer how many knots are needed from how many unmasked points it sees.
  • Unused queries still take part. No tgt_key_padding_mask is passed, so queries beyond K join decoder self-attention even though their outputs are discarded.
  • Padding is handled twice. point_mask goes to the encoder as src_key_padding_mask and to the decoder's cross-attention as memory_key_padding_mask. That pair is the whole variable-length mechanism on the input side.
Output head

How six scores become a sorted knot vector

Knots must be strictly increasing and inside (0, 1). Rather than sort or penalise, the head makes disorder impossible: each query emits a raw score, softplus makes it a positive gap, a running sum stacks the gaps, and dividing by the K-th sum normalises. Try it. Whatever you do to the sliders, the K-th knot lands on exactly 1.

Queryraw rsoftpluscumsumknot urescaled

Blue dots are free knots. The pink dot is the K-th, pinned to 1.0 by cum[K−1] / cum[K−1]. Left alone it would collide with the four clamped end knots and make the solve singular, so every training and evaluation path applies 0.02 + 0.96·u first. The model therefore controls K−1 knots; the last always sits at 0.98.

# src/knot_transformer.py:274
raw        = self.knot_head(decoded).squeeze(-1)     # (B, 6)
increments = F.softplus(raw) + 1e-6                  # strictly positive gaps
cum        = torch.cumsum(increments, dim=-1)        # strictly increasing
for b in range(B):
    K = num_knots[b].item()
    knot_vals[b, :K] = cum[b, :K] / (cum[b, K - 1] + 1e-8)   # K-th knot == 1.0

experiments/REPORT.md records the attempted fix: predict K+1 gaps and divide by the (K+1)-th sum. That version collapsed to uniform spacing, so the pinned head plus rescaling stayed.

The DETR link

What DETR was for, and what this repo took from it

DETR (Carion et al., 2020, "End-to-End Object Detection with Transformers") reframed object detection as direct set prediction. A CNN turns the image into a grid of features, a transformer encoder lets every location see every other, and a decoder holds 100 learned object queries. Each query attends to the encoded image and emits one box and one class, all in parallel. That removed anchors and non-maximum suppression from the detection pipeline.

The idea worth stealing is the query. A query is a learned vector that means "slot i of the answer". It carries no input content; it gets content by cross-attending to the encoder. Because the number of slots is fixed and decoding is parallel, the model emits a variable-size answer without generating tokens one at a time. KnotTransformer needs exactly that: N points in, N−2 numbers out, N changing from sample to sample.

The whole borrowed mechanism is five lines

self.knot_queries = nn.Embedding(max_knots, d_model)
…
q_idx   = torch.arange(self.max_knots, device=points.device)

decoded = self.decoder(queries, memory,
                       memory_key_padding_mask=point_mask)

The same six vectors are broadcast to every sample in the batch. Everything input-specific arrives through cross-attention to memory.

Why the order constraint changes the story

DETR's hardest problem is deciding which query answers for which object, and Hungarian matching exists to solve it. A knot vector is sorted by definition, so the pairing is free: the first gap is the first knot. The monotonic head turns a set-prediction architecture into a sequence predictor without making it autoregressive.

The cost is the pinned last knot above. DETR's "no object" class has no equivalent here, so the model cannot learn to leave slack at the end of the interval on its own.

Training

Two phases: imitate a heuristic, then beat it

Bending energy is a spiky loss. Near-coincident knots send it to infinity, and a random network produces plenty of those. So training starts by copying a safe rule of thumb and only then switches to the real objective.

Why each stabiliser is there

  • Grouping by N. The solver needs every curve in a call to have the same number of points. Sorting a mixed batch into per-length groups gives one batched solve per length instead of one per sample.
  • Energy cap. torch.clamp(max=1000) has zero gradient above the cap, so a curve with energy 50,000 contributes a constant and does not steer the update. Without it a handful of outliers own every step.
  • Chord-filtered data. Training only on samples where chordal already gives E < 1000 keeps the starting point inside the cap.
  • Checkpoint by held-out ratio. The script's header says why: training loss and held-out generalisation diverge after about 30 epochs, so the lowest training loss is the wrong model to keep.
  • Chunked resume. Each invocation runs CHUNK epochs and saves model, optimiser, and trajectory to one state file. The notebook does the same against Google Drive to survive Colab disconnects.

Two Phase 2 loops exist. Only one was used.

Phase2Trainer inside src/knot_transformer.py is the first draft: one solver call per sample, lr 1e-4, batch 512, no energy cap, no boundary rescale, a filter that keeps only samples already beating chordal, and best-by-training-energy checkpoints. Because it skips the rescale, its K-th knot is exactly 1.0 and the knot vector is degenerate. The results in the README come from train_phase2_longer.py and the notebooks, which fix all of that. If you extend training, start from the script.

Geometry layer

The loss function is a B-spline solver

src/curvature_layer_nd.py has no trainable weights. It is ordinary PyTorch tensor code, so autograd differentiates it. Four steps turn knots into a scalar.

1 · Build A(u) construct_A

For N points the knot vector has N + 6 entries and the curve has N + 2 control points. Rows 1…N evaluate the cubic basis at the knots themselves, so data point i is interpolated at parameter ui. The first and last rows set the second derivative to zero at each end (natural end conditions).

2 · Solve solve_nd

A(u) · P = [0, D₁, …, D_N, 0]ᵀ

Done with torch.linalg.inv_ex and a batched matmul per coordinate. Differentiating the inverse gives the implicit-function gradient the README quotes:

∂P/∂u_k = −A⁻¹ (∂A/∂u_k) P

3 · Differentiate the curve first_/second_derivative_nd

Derivatives of a B-spline are B-splines of lower degree whose control points are scaled differences. Two passes give C′ (degree 2) and C″ (degree 1), each evaluated with de_boor.

4 · Integrate global_curvature_nd

κ = ‖C″ − proj_{C′} C″‖ / ‖C′‖² E = ∫₀¹ κ² ‖C′‖ dt

The projection form of curvature works in any dimension and reduces to the familiar |x′y″ − y′x″| / ‖C′‖³ in 2D. The integral uses Simpson-style weights over 100 parameter samples.

Since any valid knot vector interpolates the data exactly, there is no fit term to balance. That is why energy alone works as a loss. It is also why the loss can be gamed: a huge loop has gentle curvature. src/losses.py adds a buffer-box penalty on control points to stop that, and the road experiments below show it over-corrected at weight 200.
